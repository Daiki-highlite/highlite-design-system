# Brandri 記事パイプライン 仕様

毎日蓄積されるトレンドサマリから週1本を選び、Highliteの見解を載せた記事に仕立て、
Slackでのレビューを経て brandri.jp に公開するまでを定義する。

---

| 前提 | 状態 |
|---|---|

| Slack Bot Token（`reactions:read` / `reactions:write` / `chat:write` / `channels:history`） | 要確認。チャンネル `C0BNHP6HU04` にbotを招待すること |

## 1. 全体フロー

```
[毎日]  サマリ蓄積        marketing/articles/ ← 既存フロー
                                ↓
[水曜]  ① 選定           直近7日分から1本を構造的に選ぶ（+ 選定理由をログ化）
                                ↓
        ② 執筆           Highlite視点の記事を生成 → drafts/ に .md
                                ↓
        ③ 提示           Slackに投稿（メタ＋リード＋GitHubリンク）→ slack_ts を記録
                                ↓
[毎日]  ④ 同期           リアクション／コメントを読み取り、状態遷移・記事修正
                                ↓
[翌週木] ⑤ 公開          最終確認 → 公開 → ✅ ＋ URLコメント
```

**定常状態では毎週水曜に1本投稿され、翌週木曜に1本公開される。**
レビュー期間は8日間。修正が1〜2回入っても公開日に間に合う。

## 2. 選定フェーズ（水曜）

### 2.1 対象

`paths.summaries` 配下の、直近 `cadence.selection_window_days`（7日）分のサマリ。
すでに記事化済み・選定除外済みのものは対象から外す。

### 2.2 スコアリング

| 軸 | 配点 | 判定内容 |
|---|---|---|
| Highliteの独自見解 | 0-3 | ブランド判断基準／デザイン内製化／AI実装の文脈に接続できるか |
| **一次情報の紐付け** | 0-3 | track-record.md の実案件に具体的に接続できるか |
| ターゲット適合 | 0-2 | `content.target_clusters` のいずれかに刺さるか |
| 鮮度の持続 | 0-2 | 4週間後に読まれても価値が残るか |

**最高点のものを1本選ぶ。ただし以下は選定不可：**
- 合計7点未満
- 一次情報の軸が0点（＝実案件に紐付かない → 引用だけの記事になる）

全候補が条件を満たさない場合は**記事化を見送る**。その週は投稿しない。
無理に書くより空ける。

### 2.3 選定ログ

`paths.selection_log` に追記する。落とした6本の理由も残す。

```markdown
## 2026-08-12（水）

**選定：** 2026-08-09-summary.md「AI生成物の品質基準」
スコア 9/10（独自見解3 / 一次情報3 / 適合2 / 鮮度1）
→ 久留米総合美容外科のMVV策定時、AI出力の採否基準を作った経験に直結

**見送り：**
| サマリ | スコア | 理由 |
|---|---|---|
| 2026-08-10-summary.md | 5 | 一次情報0。関連案件なし |
| 2026-08-08-summary.md | 6 | 鮮度0。2週間で陳腐化する速報 |
| ... |
```

これは記録であると同時に、**選定基準の妥当性を後から検証するためのデータ**になる。
数ヶ月分溜まったら、実際に反応が良かった記事とスコアの相関を見て配点を調整する。

## 3. 状態モデル

### 3.1 状態一覧

| status | 判定条件 | botの動作 |
|---|---|---|
| `draft` | Slack投稿済み・リアクションなし | `reminder_after_days` 経過でリマインド1回 |
| `reviewing` | 👀 あり／未処理コメントなし | 待機 |
| `revision_requested` | 👀 あり／**未処理のスレッドコメントあり** | 記事修正 → v{n}返信 → コメントに☑️ → 👍を剥がす |
| `approved` | 👍 あり | 公開キューへ |
| `scheduled` | 👍 ＋ 🗓️ | 予定日まで待機。同期のたびに👍存続を確認 |
| `published` | ✅ | 完了。同期対象外 |
| `dropped` | 🗑️ あり | `dropped/` へ移動 |
| `expired` | `ttl_days` 超過かつ未公開 | 鮮度切れをコメント → `dropped/` へ |

### 3.2 リアクション定義

| 絵文字 | 付与者 | 意味 |
|---|---|---|
| 👀 `eyes` | 人 | レビュー中／修正依頼中／再レビュー中 |
| 👍 `+1` | 人（**チャンネルメンバーなら誰でも可**） | 承認。外すと承認取り消し |
| 🗑️ `wastebasket` | 人 | ボツ |
| 🗓️ `spiral_calendar_pad` | **bot** | 公開日確定 |
| ✅ `white_check_mark` | **bot** | 公開済み |
| ☑️ `ballot_box_with_check` | **bot** | スレッドコメントの修正反映済み（コメント側に付与） |

承認者の限定は行わない（`slack.restrict_approvers: false`）。
ただし**bot自身の👍は承認としてカウントしない**。

想定される典型的な流れ：

```
水  botが v1 を投稿
    ↓
    レビュー開始 → 👀
    ↓
    修正コメント → botが v2 を出力（👀 のまま）
    ↓
    再レビュー（👀 のまま）
    ↓
    問題なし → 👍           ← ここで初めて承認
    ↓
翌週木  最終確認 → 公開 → ✅
```

### 3.3 重要ルール

**R1. 承認の管理は人が行う。botは👍に触れない**

運用ルール：
- 👍を付ける ＝ その時点の版を承認
- 👍を外す ＝ 承認を取り消す
- 修正依頼中・再レビュー中は 👀 のまま

botは👍の付け外しを一切行わない。
「承認するが、このタイポだけ直しておいて」というケースで、
botが👍を剥がすと不要な再承認の手間が発生するため。

ただし**👍が付いた状態で修正を反映した場合は、版のズレをスレッドで通知する**。

```
修正を反映しました（v2）

{変更点の要約}

👍がついた状態での修正です。内容を確認し、
承認を取り消す場合は👍を外してください
```

判断は常に人の側に残る。公開直前の最終確認（R2）があるため、
レビュー期間8日間のどこかで👍を外せば公開は止まる。

`review.revoke_approval_on_revision: true` にすると、
修正のたびにbotが👍を剥がして再承認を必須にする挙動へ切り替わる。

**R2. 公開直前に必ずリアクションを再取得する**

sync は実行した瞬間のSlackしか見ていない。前回の sync 以降に👍が取り消されると、
状態ファイルの `scheduled` は古い情報になる。

```
木 09:00  /brandri-sync   → 👍あり → scheduled のまま記録
木 09:30  👍が取り消される  ← 誰も見ていない
木 10:00  /brandri-publish → 状態ファイルを信じると、取り消した記事が公開される
```

publish は状態ファイルを信用せず、実行時に `reactions.get` を叩いて再確認する。
これにより sync の実行頻度に関係なく取り消しを取りこぼさない。

**R3. 未処理コメントの判定**

スレッド内のメッセージのうち、
- `slack.bot_user_id` の投稿ではない
- かつ ☑️ が付いていない

ものを「未処理の修正依頼」とみなす。処理後に必ず ☑️ を付ける。
これを忘れると、次回の同期で同じ修正を再適用する無限ループになる。

**R4. 承認 ≠ 公開確定**

`approved` は公開キューへの登録にすぎない。実際の枠割り当ては公開フェーズで行う。

## 5. 記事の構成テンプレート

トレンドサマリの引用が主、Highliteの見解が従、という構成は採用しない。
引用の主従が逆転して著作権上のリスクがあり、かつAEO上も一次情報のない記事は評価されないため。

### 5.1 必須構成

| セクション | 内容 | 分量 |
|---|---|---|
| リード | 読者の課題を一文で刺す。トレンド解説から入らない | 100〜150字 |
| ① 何が起きているか | 外部の動きを**自分の言葉で**要約。出典リンク必須 | 300〜400字 |
| ② Highliteはこう見る | 独自の解釈と判断。**記事の主題** | 500〜700字 |
| ③ 実務ではこうだった（必須） | 実案件・実体験の具体。数字と固有の状況を含む | 400〜600字 |
| ④ 明日できること | アクション2〜3個 | 200〜300字 |
| CTA | highlite.co.jp への内部リンク | — |

**③が書けない題材は選定段階で落とす。**

### 5.2 引用ルール

- 直接引用は1記事1箇所・50字以内
- 要約は必ず自分の言葉に。原文の語順・段落構成をなぞらない
- 出典URLは記事末尾に必ず記載

### 5.3 文体ルール

`skills/_shared/brandri-strategy.md` に従う。要点：

**やること** — 短く言い切る／段落を意図的に切る／具体的な数字と固有名詞／主張には根拠

**やらないこと** — 対比構造の反復／詩的な締め／説明過多／読者の自己選別を促す言葉／「いかがでしたか」等の定型句

**禁止語** — 効率化／コスト削減／AI自動生成／大量生成

**推奨語彙** — ブランドの本質を守りながら実装スピードを上げる／組織としてのブランド判断基準

## 7. 公開フェーズ

### 7.1 枠の割り当て

投稿時点で `投稿日 + publish_lead_days` 直後の `publish_day` を仮の公開予定日とする。
承認された時点で確定し、botが 🗓️ を付与してスレッドに予定日をコメントする。

複数本が同じ枠に競合した場合は `expires_at` が近い順 → 承認日時が古い順。

### 7.2 公開当日

1. **最終リアクション確認**（R2）— `reactions.get` で親投稿を再取得
2. 👍が消えている／🗑️が付いている場合：
   - 🗓️ を剥がす
   - スレッドに「公開をキャンセルしました」とコメント
   - `drafts/` へ戻す → **公開処理は実行しない**
3. 確認が通れば `publish.mode` に応じて公開
4. 完了後：✅ を付与 → スレッドに公開URLを返信 → front matter更新 → `published/` へ移動

### 7.3 公開手段（**要決定**）

| mode | 処理 | 状態 |
|---|---|---|
| `manual` | 最終原稿を出力して入稿を促す。URLは人から受け取る | **現状これ** |
| `repo_pr` | 対象リポジトリにPRを作成 | 未実装 |
| `cms_api` | CMSのAPIを叩いて投稿 | 未実装 |
